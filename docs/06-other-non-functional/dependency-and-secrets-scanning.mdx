<TLDR>
Your app is mostly other people's code, and that code has known bugs. A dependency scanner compares your package versions with a list of published advisories. A secret scanner looks for passwords and keys committed by mistake. This page runs a real dependency scan on TaskFlow and reports what it found.
</TLDR>

## What and why

A **dependency** is a library your app uses, such as FastAPI. Each one can pull in more packages, so a typical Python app has many more installed packages than the ones you named.

A **vulnerability** in a dependency is a published bug or weakness. It is usually fixed in a newer version. Your app stays exposed until you upgrade, even if your own code is correct.

A **secret** is a value that must stay private: a password, an API key or a token. A **secret leak** happens when one is stored where others can read it, such as a git commit or a log file. Deleting the line later does not remove it from git history, so treat a leaked secret as exposed and change it.

## How it works

**Dependency scanners** read your package list and versions, then compare them with a database of advisories. Each advisory has an ID, the affected versions and often a fixed version. The scanner does not run your app, so it does not prove that the bug can be reached.

**Secret scanners** search files and git history for patterns, such as the shape of a cloud key or a line like `password = "..."`. They produce false positives, so a person must check each hit.

Both are filters, not verdicts. A clean scan does not mean the code is safe.

## When to use it (and when not to)

| Use it when | Skip or limit it when |
|---|---|
| A dependency file changes, in every build | You treat a clean run as proof of safety |
| A repository could hold credentials, such as CI files or `.env` files | You scan a private registry without permission |

## TaskFlow example

The local app pins its direct dependencies in `examples/taskflow/requirements.txt`, which has five lines. Create a virtual environment for the scanner, so it does not mix with the app, then scan the file:

```bash
python3 -m venv /tmp/venv-s1
/tmp/venv-s1/bin/pip install --index-url https://pypi.org/simple pip-audit
/tmp/venv-s1/bin/pip-audit -r examples/taskflow/requirements.txt
```

`pip-audit` is a tool for scanning Python environments for packages with known vulnerabilities. This run used `pip-audit` 2.10.1.

:::info[Real run, 2026-11-06]
This output is from a real run against the TaskFlow requirements file, not an example. It needed network access to the default vulnerability service.

- Packages checked: 14. That is the five pinned packages plus nine packages they depend on (pip-audit lists all 14 in its JSON output).
- Findings: 14 records, all for one package, `starlette` version 0.41.3. They cover 7 advisory IDs. Starlette comes in through `fastapi`.
- Exit code: 1, which means vulnerabilities were found.
:::

Each row of the table has four columns. Take `starlette 0.41.3 PYSEC-2026-1941 0.47.2`:

| Column | Meaning | Example |
|---|---|---|
| Name | The package with the problem | `starlette` |
| Version | The version you have installed | `0.41.3` |
| ID | The advisory identifier. Search for it to read the details | `PYSEC-2026-1941` |
| Fix versions | Versions that contain the fix | `0.47.2` |

The highest fix version in this output is 1.3.1, so a Starlette at or above it clears every listed advisory. That is a reading of the table, not a tested upgrade. Starlette is a dependency of FastAPI, so you may also need a newer FastAPI. Run your tests after any upgrade.

### Secret scanning

Two common open-source secret scanners are gitleaks and `detect-secrets`. The gitleaks README says the project is feature complete and will get only security fixes, so check its status before you adopt it. The idea is the same for both: scan the files and history for secret-shaped text.

```bash
# not run here: scans the git history of the current repository
gitleaks detect --source . --verbose
```

The TaskFlow code has demo passwords in `examples/taskflow/app/main.py`. The seed function creates `alice` with password `alice-pass` and `bob` with password `bob-pass`. The module comment says passwords are stored in plain text on purpose, for demo use only.

:::warning[Do not copy these values]
The demo passwords let the tests and the UI log in. They are not an example of how to store credentials. Do not reuse the values, the plain-text storage or the in-memory token dictionary in a real app. A real app stores only salted password hashes and reads secrets from its environment or a secret manager.
:::

Whether a scanner flags those lines depends on its rules, so do not assume either way.

## Do this

- Scan dependencies on every change to a dependency file, and in CI.
- Record each finding: package, installed version, fixed version and advisory ID. Upgrade, then re-run your tests.
- If a real secret leaked, rotate it first. Removing it from the code comes second.

## Avoid this

- Ignoring a finding without writing down why it does not apply.
- Putting a real secret in a test file because it is "only for tests".
