<TLDR>
A flaky test passes and fails on the same code. Reproduce it first, then name the cause. Fix it if the fix is small. Otherwise quarantine it with an owner and a date, so it stops blocking others but is not forgotten. The background is in [flaky tests](/automation-engineering/flaky-tests).
</TLDR>

## Checklist

1. **Record the failure.** Save the test name, the error, the build link and the commit.
2. **Rerun it alone.** Run it 20 to 50 times in a loop. If it never fails alone, suspect shared state or order.
3. **Rerun it in the full suite.** Use the same order and the same parallel settings. See [parallel and distributed execution](/automation-engineering/parallel-and-distributed-execution).
4. **Change one thing at a time.** Random order, fewer workers, a slower machine. Note which change makes it fail more.
5. **Classify the cause.** Common groups: timing and waits, shared or leftover data, order dependence, an unstable external service, time or date logic, environment differences.
6. **Decide: fix or quarantine.** Fix now if the cause is clear and small. Quarantine if it needs a larger change.
7. **Quarantine safely.** Move the test to a separate, non-blocking run. Add an owner, a ticket and a date to remove it.
8. **Fix the cause, not the symptom.** Replace a fixed sleep with a wait on a condition. Give each test its own data.
9. **Prove the fix.** Rerun the loop from step 2 with no failures.
10. **Track it.** Count flaky tests and quarantine age. See [maintaining automation suites](/automation-engineering/maintaining-automation).

## Example: a shared-data flake

A test creates a task titled "Demo task" and then lists tasks expecting exactly one. It passes alone but fails when another test also creates "Demo task". The cause is shared data. The fix is to give each test its own project, or to look up the task by the ID returned from the create call.

```bash
# Run one test 30 times and stop at the first failure
for i in $(seq 30); do pytest -q -x tests/test_x.py::test_name || break; done
```

This loop is a pattern, not run here.

:::tip
A retry that hides a failure is not a fix. If you add a retry, keep reporting the first failure.
:::

## Done when

- The cause is named in the ticket.
- The test passes the repeat loop, or sits in quarantine with an owner and a date.
- The blocking suite is green and trusted again.
