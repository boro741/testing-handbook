## What and why

Tool claims change fast. This directory records what we could verify, and the date we checked it. Use it as a starting point, then check the repo yourself before you adopt a tool.

Each row has the same columns, so you can compare tools side by side. Stars are not in the table on purpose. They are not evidence of production readiness ([The AI testing landscape](/ai-in-testing/ai-testing-landscape) explains why).

**Adoption evidence types.** Each claim is one of four types:

- **Documented production use:** a company describes its own setup in a primary source.
- **Community recommendation:** people recommend it, without a company case.
- **Individual experiment:** one person's trial.
- **Vendor marketing:** the maker's own claim.

**Dates.** "Last release" is the latest GitHub release shown by the repo's release API, with the date it was published, as of 2026-11-06. Where the repo shows a sub-package tag, we say so.

## How it works

Use the table in three steps:

1. Filter by the problem you have. Browser automation, AI evaluation, API test generation or load testing.
2. Check the licence. "Open-core" means a free core with paid extras, and some parts may have different terms.
3. Check the adoption evidence before you trust a claim.

## Do this

- Re-check the "last release" and licence cells before a decision. They change.
- Trial each tool on TaskFlow first, using the rules in [the TaskFlow reference](/start-here/taskflow-reference).
- Write down the adoption evidence type when you cite a tool in a decision.

## Avoid this

- Choosing a tool by star count or by a vendor page alone.
- Treating a "not verified" cell as "no".
- Reading an open-core licence as fully open source. Check which folders are covered.
